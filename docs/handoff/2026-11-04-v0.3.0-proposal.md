# HydroSeason 0.3.0: proposed method changes and what they change

Status: approved 2026-11-04 (see "Decisions taken"). Each change below alters the method, so it ships only under a new method policy, `hydroseason-v0.3.0`. The library on `main` and on branch `spatial-unit-study` still runs `hydroseason-v0.2.0`; the changes are made on branch `method-v0.3.0`.

## Decisions taken (2026-11-04)

The project lead approved the recommended option for each decision below.
- **A:** approved.
- **B:** approved, in the widen form.
- **B2:** the draft plan approved with every open choice as proposed, and frozen. It ran on 2026-11-04 and **passed**: on known truth, relaxing does not make refuge labels worse where both rules give them, and the refuge labels it adds beat chance (kappa 0.347 synthetic, 0.382 injected). Recharge labels, reported only, also passed both rules ([results](2026-11-04-b2-refuge-labels-results.md)).
- **C:** decided by B2, so adopted.
- **Packaging:** A + B + C ship together as `hydroseason-v0.3.0`.

Two implementation steps below differ from what this proposal listed. The branch starts from `spatial-unit-study`, not from `main` after a merge, so `main` is left for the lead to merge. The package version is not yet set to 0.3.0, because the 0.2.1 patch is still pending and a test pins 0.2.0.

The 0.2.1 patch ([release plan](../../RELEASE_PLAN_0.2.1.md)) is separate. It fixes input handling and changes no method behaviour.

## Summary

Three changes are proposed. Every other part of the method stays as it is in 0.2.0.

| | Change | What it changes in the method | What users see | Evidence | Ready? |
| --- | --- | --- | --- | --- | --- |
| A | Complete the method fingerprint | Nothing computed changes | A new policy id and fingerprint on every output | G2 audit | Yes |
| B | Make the trough timing label agree with the reported trough month | The trough timing label, and only where it names a different month from the boundary | About 10% of `point` troughs on small areas (about 59–236 km²) and about 3% on subbasins and tiles lose `point` and their `trough_date`. No boundary, date or route moves | Real-record measurement, known-truth exploratory finding | Yes, once the lead picks one of two forms |
| C | Let any dated cycle anchor the condition baseline, not only `point` cycles | Which cycles the annual condition labels are ranked against | About ten times as many units get recharge and refuge labels; some existing labels shift | B1 known truth (recharge only, mixed), real-record measurement | No: after the B2 test. The labels it adds were weak on known truth |

**Recommendation.**
- Ship A, B and C together as `hydroseason-v0.3.0`, after the condition-label test (B2) reports.
- Settle C on B2's result, not on coverage. Relaxing labels far more units, but on known truth the recharge labels it adds were only weakly informative, or no better than chance, and refuge labels have never been scored.
- Ship B without C only if B2 rules C out. Under today's baseline rule, B removes a quarter of the few baselines that exist (see "How B and C interact").

## What stays the same

These were tested in November 2026 and are not proposed for change:
- **Identifiability gates.** The amplitude must be at least 3.0 times the detectability floor, and the peak must hold at least 5 water pixels. Looser gates reproduced as well (G1) but dated less accurately (G2).
- **Trough tolerance.** No wider tolerance passed (L1).
- **Direction of the trough label.** It still compares the months from the peak to the boundary. Adding the months after the boundary barely helped (L2).
- **The trough boundary as the dry-to-wet anchor.** A rise rule did not do better overall (R1).
- **Everything that places a cycle**, none of which any proposal touches:
  - trough boundary detection, cloud screen, search window and trough refinement;
  - `trough_boundary_date`, `start_date` and `end_date`;
  - peaks;
  - the seasonality test and routing;
  - event detection;
  - the monthly condition.

## A. Complete the method fingerprint

**Today.** The method policy manifest ([`hydroseason/_method_policy.py`](../../hydroseason/_method_policy.py)) pins:
- the event thresholds;
- the seasonality test;
- the recurrence policy;
- trough refinement.

Its SHA-256 is the `method_policy_fingerprint` stamped on every `CatchmentAnalysis` and run manifest. It leaves out three sets of method constants:
- **The timing-identifiability gates** (`TIMING_IDENTIFIABILITY_DEFAULTS` in `_scientific_defaults.py`):
  - amplitude-to-floor ratio 3.0, 5 peak water pixels;
  - spans for `point` (0 months), `interval` (2) and `broad` (5);
  - at least 7 informative cycles to keep per-year detection.

  The `broad` span is a class default and is not written into the generated defaults either. A strict expected-failure test, `test_manifest_covers_timing_identifiability_gates`, records the gap.
- **The condition baseline:** at least 5 eligible cycles, labels at the 20th and 80th percentiles, and the eligibility rule itself.
- **The trough-label rule** that change B adds.

The manifest generator only refuses to run on a dirty tree for the files in `SCIENTIFIC_SOURCE_FILES`. That list leaves out the modules that implement the gates, the label and the baseline: `_timing_identifiability.py`, `_dynamic_year.py`, `_boundary.py` and `_condition.py`. So a change to any of them today neither moves the fingerprint nor blocks manifest generation.

**Proposed.**
1. Add three blocks to the manifest:
   - `timing_identifiability`: every threshold, including the `broad` span, plus its fingerprint and authority scope;
   - `condition_baseline`: the eligible timing statuses, minimum cycles and percentiles;
   - `trough_label`: the consistency rule from B, by name and version.
2. Add the four modules to `SCIENTIFIC_SOURCE_FILES`.
3. Set `policy_id` to `hydroseason-v0.3.0`.
4. Generate `docs/method-policy-v0.3.0.json` and its `.sha256` from a clean tree.
5. Replace the expected-failure test with a passing one.

**Effect on behaviour.**
- No computed value changes.
- Every output carries `method_policy_id = "hydroseason-v0.3.0"` and a new `method_policy_fingerprint`.
- The run manifest's method section gains the three blocks.
- From then on, any change to a gate, the baseline rule or the label rule changes the fingerprint.

**Limit.** `analyze_catchment` and `run_hydroseason` expose no gate or baseline settings, so every public run uses the policy values. Callers who build their own `DynamicHydroYearConfig` for the lower-level detectors can still run other values under the same fingerprint, as today.

## B. Make the trough timing label agree with the reported trough month

### The defect

Two parts of a cycle's trough are decided separately:
- **The boundary month** (`trough_month`, exported as `trough_boundary_date`, and as `trough_date` when the label is `point`). It is the lowest clear month (at most 20% invalid) within a search window around the expected trough.
- **The trough timing label** (`trough_timing_status`, with `trough_interval_start`/`_end`).
  - It compares every usable month from the cycle's last peak month to the boundary, cloudy months included, within the detectability floor.
  - On refined troughs, it comes from the refinement's candidate months up to the boundary.

When the label singles out a different month from the boundary, the row reports `point` for a month the label did not single out. On real records ([results](2026-11-03-real-record-impact-results.md), M2):

| Units | `point` troughs | Label on another month |
| --- | ---: | --- |
| G1 windows, core (about 236 km²) | 3,843 | 472 (12.3%) |
| G1 windows, quadrants (about 59 km²) | 10,918 | 1,008 (9.2%) |
| Subbasins and tiles (HydroBASINS levels 6–8 and matching tiles) | 4,766 | 157 (3.3%) |
| Whole case-study catchments | 22 | 0 |

- The label's month is always earlier than the boundary.
- On the G1 windows, the gap is one month in 25% of cases. The median is 3 months and the largest 14.
- Causes (exploratory):
  - in 47% of cases, the label's month is the raw minimum that the cloud screen removed;
  - in 33%, the record flags a lower month outside the boundary's search window;
  - 20% fit neither.
- On injected known-truth records the same thing happened in 13% of `point` troughs ([L2 results](2026-11-03-l2-r1-results.md)).

### Two forms of the fix (the lead picks one)

1. **Widen (recommended).**
   - After the boundaries are final, if `trough_month` lies outside the label's interval, widen the interval to cover both months.
   - Give the result the status the existing width rule gives that span: up to 2 months apart is `interval`, up to 5 is `broad`, and wider is `unresolved`.
   - Strengths:
     - it covers every case by construction;
     - it never claims more precision than the evidence holds;
     - it changes only cycles that have the defect;
     - running it after the boundary passes means no boundary can move.
2. **Screen.** Judge the label only on the months the boundary could choose: clear months within the search window.
   - Strengths: it covers the cloud cases (at least 47% and at most 85–89% of the defect), and it can leave some of them `point`.
   - Weaknesses:
     - it changes the label's comparison set for every cycle, not only the defective ones;
     - it would need its own known-truth check;
     - cases outside the search window can remain.

### Effect on behaviour (widen form, simulated on the stored real-record runs)

The simulation ([`scripts/v030_label_fix_impact.py`](../../scripts/v030_label_fix_impact.py), output [2026-11-04-v0.3.0-label-fix-impact.json](2026-11-04-v0.3.0-label-fix-impact.json)) applies the rule to the 3,010 records routed to per-year detection.

| | G1 windows (2,001 records) | Spatial-unit study (1,009 records) |
| --- | --- | --- |
| `point` troughs | 14,761 | 4,788 |
| Troughs that change | 1,480 (10.0%) | 157 (3.3%) |
| … become `interval` / `broad` / `unresolved` | 627 / 486 / 367 | 56 / 48 / 53 |
| Cycles whose aggregate `timing_status` changes | 1,131 | 138 |
| Records with one fewer informative trough | 272 | 47 |
| Records that would re-route to event characterisation | 0 | 0 |

**Columns that change**, on the affected cycles only:
- `trough_timing_status`;
- `timing_status`, where the trough was the stronger of the two;
- `trough_interval_start_date` / `_end_date`, widened;
- `trough_date`, which becomes blank, as for every non-`point` trough;
- `baseline_eligible` and the condition labels, through `timing_status` (see "How B and C interact").

**Reports:**
- the "point identifiable" count on the summary card;
- the trough marker, which is drawn open instead of filled.

**Unchanged:**
- `trough_month` / `trough_boundary_date`;
- `start_date`, `end_date`, `hy_start`, `hy_end`;
- peaks, trough extent and trough refinement;
- routing: the 7-informative-cycle rule still holds for every record.

**For hydropools:** their clocks read `trough_boundary_date`, which does not move. Code that filters on `trough_date` will see fewer dates on small areas.

## C. Let any dated cycle anchor the condition baseline

### Today

A cycle anchors the annual condition baseline only if:
- it is `complete`;
- its boundary is `confirmed`;
- its peak is not `anomalous`;
- its aggregate `timing_status` is `point` (`_condition.py`; the code comment calls this "a defensible exact date").

A unit needs at least 5 eligible cycles. Then every cycle is ranked against them:
- **recharge** from the peak extent;
- **refuge** from the trough extent;
- `low` at or below the 20th percentile and `high` at or above the 80th.

With fewer than 5 eligible cycles, every cycle reads `insufficient_baseline`.

### Proposed

Accept any dated aggregate status: `point`, `interval` or `broad`. `unresolved` cycles stay out, and the other three conditions are unchanged.

Dropping the timing requirement altogether gives almost the same result on real records. The proposal keeps `unresolved` out because such a cycle has no bounded trough or peak timing at all.

### Evidence

- **Recharge labels, known truth (B1)** ([results](2026-11-03-l1-followups-results.md), recomputed from its JSON). Two questions get different answers.

  | Agreement with the truth | Synthetic | Injected |
  | --- | ---: | ---: |
  | Cycles today's rule labels (4.9% and 21.7% of cycles) | 0.682 | 0.479 |
  | The same cycles, relaxed rule | 0.723 | 0.503 |
  | Cycles only the relaxed rule labels | 0.520 | 0.417 |
  | Expected if labels were independent of the truth | 0.440 | 0.423 |

  - **Where both rules give labels, relaxing makes them no worse.** The larger baseline helps a little.
  - **The labels relaxing adds are weak.** They are a little better than chance on synthetic records and no better than chance on injected ones.
  - They sit in records with weaker seasons, which today's rule never reaches. Injected records also understate accuracy, because their truth leaves out the real background's own wet and dry years. Even today's labels there are close to chance.
  - **Correction.** Earlier summaries said B1 found the relaxed rule "at least as accurate" without this qualifier: the B1 summary, the real-record results and the decision record. They are corrected as of 2026-11-04.
- **Coverage on real records** ([results](2026-11-03-real-record-impact-results.md), M1):
  - units with a baseline rise from 5.4% to 62.3% (G1 core) and from 4.7% to 45.4% (G1 quadrants);
  - on subbasins and tiles, from 0–5% to 30–61%.
- **Repeatability between independent pixel halves of the same place:**
  - Recharge: agreement on the added labels minus today's is −0.025 [−0.104, +0.052]. No cost appears on any measure. Repeatability is not accuracy, though: two halves can agree on an uninformative label.
  - Refuge: the same comparison gives −0.014 [−0.096, +0.069], which is inconclusive. Chance-corrected agreement (exploratory) is lower in the added units: kappa 0.41 against 0.51, difference −0.10 [−0.22, +0.02].
  - Today's rule labels only 16 of the 256 windows, so more real-record runs cannot narrow this.
- **Refuge labels have never been scored against a known truth.** The draft B2 plan ([2026-11-04-b2-refuge-labels-plan.md](2026-11-04-b2-refuge-labels-plan.md)) does that. It reruns G2's generators with a dry level that varies between seasons, on fresh seeds: 1,400 synthetic and 1,148 injected records. It asks two questions, in both arms:
  1. **Rule 1.** Where both rules give labels, does relaxing make refuge labels worse? Accuracy under the relaxed rule minus today's; it holds if the 95% interval's lower end is at least −0.05.
  2. **Rule 2.** Do the refuge labels relaxing adds carry information? Cohen's kappa with the truth; it holds if the 95% interval's lower end is above 0.

  Recharge labels are scored under the same rules and reported. B2 does not compare the added labels with today's, because that comparison also measures which records each rule reaches. The run takes about half an hour.

### Effect on behaviour

**Columns that change for many more units:**
- `baseline_eligible` and `baseline_n`;
- `peak_percentile` and `trough_percentile`;
- `recharge_condition`, `refuge_condition` and `annual_condition`, plus their `_qualified` versions;
- `consecutive_dry_cycles` and `consecutive_wet_cycles`.

The full-record, fixed-period and rolling baselines all use the same eligibility, so all three relax.

**Units that already have labels:** 13.0% of recharge and 16.5% of refuge labels change, because the baseline grows and some ranks cross a percentile.

**Case studies (2005–2025 records):**
- The Gilbert gains a baseline (9 eligible cycles) and labels for all 21 years.
- The Daly (4 eligible) and the Fitzroy (3) stay below five.
- The Lachlan and the Moonie route to event characterisation, so they have no labels under either rule.

**Unchanged:**
- the monthly condition, which ranks usable months, not cycles;
- all timing and boundaries;
- routing.

**Docs to update:**
- `baseline_eligible` in `report-columns.md`;
- `hydrological-state.md`;
- the guide;
- the code comment that calls `point` a defensible exact date.

## How B and C interact

B removes `point` from some cycles, and today's baseline admits only `point` cycles. So B alone shrinks today's baselines, which are already scarce. Under C, a cycle that becomes `interval` or `broad` stays eligible; only one that becomes `unresolved` leaves. Simulated on the stored runs:

| | Today's rule (`point` only) | C (any dated status) |
| --- | --- | --- |
| G1 eligible cycles lost to B | 247 of 2,549 (9.7%) | 92 of 9,394 (1.0%) |
| G1 units that lose their baseline | 25 of 97 (26%) | 15 of 984 (1.5%) |
| Subbasins and tiles: eligible cycles lost | 24 of 1,087 (2.2%) | 14 of 3,814 (0.4%) |
| Subbasins and tiles: units that lose their baseline | 3 of 26 | 1 of 356 |

## Decisions requested

1. **A:** approve.
2. **B:** approve, and choose the widen form (recommended) or the screen form.
3. **C:** choose one:
   - review and approve the draft B2 plan, then decide on C after B2 reports (recommended);
   - relax now, documenting that the added labels are weak on known truth and that refuge labels in newly labelled units are less repeatable;
   - keep today's rule.
4. **B2's open choices**, before it is frozen:
   - its two rules, in place of comparing the added labels with today's;
   - the floor in rule 2: kappa above 0 (proposed), or 0.20, the lower bound of "fair" agreement in Landis and Koch (1977). On B1's numbers, 0.20 would likely fail even today's recharge labels on injected records;
   - whether recharge labels also decide. If they do, C could fail as a whole: on B1's numbers, the recharge labels relaxing adds fail rule 2 on injected records. No recommendation here; it turns on how much weight the injected arm deserves, given that its truth leaves out the background's own wet and dry years;
   - the dry-level spread: uniform between 0 and 0.9 season amplitudes, matched to the spread of the peaks.
5. **Packaging:** ship A + B + C together as `hydroseason-v0.3.0` once B2 reports (recommended). If B2 does not support C, the choices are:
   - ship C anyway, with the caveats in the docs;
   - or ship A + B under today's baseline rule and accept the coverage loss shown above.

## Implementation and checks, after approval

1. Merge `spatial-unit-study` into `main`.
2. Make the changes on a new branch, with unit tests for each rule:
   - B: an interval that misses the boundary is widened and re-graded, and no boundary column changes.
   - C: an `interval` or `broad` cycle is eligible, and an `unresolved` one is not.
3. **Before/after check** on the five case studies and a sample of G1 windows:
   - every boundary, date, peak and route column is identical;
   - only the columns listed under B and C differ.
4. Rerun the real-record measurement with the new library:
   - the label/date mismatch must be zero;
   - coverage should match the figures above.
5. Rescore the stored L1 and L2 known-truth runs, and report the `point` miss share before and after B. This is reported, not used to decide.
6. Generate the v0.3.0 manifest from a clean tree, and run the full test suite.
7. Update the docs, and add a CHANGELOG "Changed" entry with a migration note:
   - condition labels and trough timing labels differ from 0.2.x;
   - boundaries, dates and routes do not;
   - compare files across versions only on unchanged columns, and use the policy id or fingerprint to tell them apart.
8. Set version 0.3.0.
