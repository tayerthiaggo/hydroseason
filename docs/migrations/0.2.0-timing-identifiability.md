# Migrating to 0.2.0: zero-dominated timing protection

`established_0_2_0` replaces `established_0_1_1` as HydroSeason's public
decision policy. It changes what the package will claim about *when* an
annual peak or trough occurred, without changing how it treats zero-water
observations as data. Read this note before upgrading if downstream code
consumes `regime`, `route`, `peak_date`/`trough_date`, `n_timing_years`, or
the compact CSV bundle.

## What did not change

- **Exact zero extent with valid pixels remains a valid dry observation.**
  It is never converted to missing, and a record is never rejected solely
  because its zero-month percentage is high.
- **Flat and below-floor years still contribute to dry-duration and event
  summaries.** Only their peak/trough *timing* observation is withheld.
- **A detectable single wet pulse can still identify a peak** even when the
  remainder of the year is zero.
- The five protected case-study catchments (Daly, Fitzroy, Gilbert, Lachlan,
  Moonie) keep their checked seasonal/aseasonal outcomes and dates.

## What changed

### A new timing-identifiability layer

Every qualifying year's peak and trough are now independently classified:

```python
TimingStatus = Literal["point", "interval", "unresolved"]
```

- `point`: a defensible single-month extremum.
- `interval`: a defensible bounded span (e.g. a broad low-water plateau) but
  no single date.
- `unresolved`: a flat/below-floor year, or an extremum that does not clear
  the calibrated detectability floor.

Classification uses a detectability floor derived from measurement
tolerance, the record's own robust noise estimate, and pixel resolution when
count data is available -- never from zero frequency. `n_zero_months`,
`zero_month_fraction`, and `n_whole_zero_years` are reported but never enter
a detectability or route decision.

### Route now requires identifiable timing, not just a seasonal/marginal regime

Previously, `route == "per_year_detection"` whenever `regime` was `seasonal`
or `marginal`. Under `established_0_2_0`, that regime condition is necessary
but no longer sufficient: the record's `timing_evidence` must also be
`supported`.

```python
TimingEvidence = Literal["supported", "insufficient", "unsupported"]
```

`timing_evidence` is `insufficient` when
`min(n_peak_timing_years, n_trough_timing_years) < min_informative_years`
(a calibrated threshold); `unsupported` when the established
seasonality/uniformity evidence already rejects an annual cycle (today
reachable only when `regime == "aseasonal"`); otherwise `supported`. A
seasonal or marginal record with insufficient identifiable timing keeps its
regime label but routes to `event_characterisation`: wet events and
low-extent spells are still reported, but no hydrological-year boundary is
published.

**Consequence:** some records that previously routed to
`per_year_detection` under 0.1.1 now route to `event_characterisation`
under 0.2.0. This is not a regression in what the record supports; it is the
new policy declining to publish a per-year boundary the underlying signal
cannot actually deliver. `route_reason` on the resulting `CatchmentAnalysis`
states which gate produced the change.

The route decision is also now checked twice: once on the record's
calendar-year timing evidence (gating whether the dynamic detector runs at
all), and again on the hydrological-year cycles that detector actually
produces (gating whether `per_year_detection` is the final route). A record
whose calendar-year evidence looks sufficient but whose real cycles cannot
resolve peak and trough timing on enough of them still falls back to
`event_characterisation`.

### Sample counts may decrease

`n_usable_years` (data/quality coverage) is unchanged in meaning, but
`n_peak_timing_years` and `n_trough_timing_years` (informative-year counts)
are new, separate fields, and `n_timing_years` -- which already existed and
kept its historical peak-derived meaning (`n_timing_years == n_peak_timing_years`)
-- may now publish a smaller value than before for records whose annual
timing is genuinely less identifiable than the pre-0.2.0 policy assumed.

### Public exact dates may become intervals or blank

`peak_date`/`trough_date` in the compact hydrological-year CSV are now
populated **only** when the corresponding `peak_timing_status`/
`trough_timing_status` is `point`. For `interval` or `unresolved`, the date
is blank. New columns carry the interval bounds and diagnostics
unconditionally:

```text
timing_status
peak_timing_status, peak_interval_start_date, peak_interval_end_date
trough_timing_status, trough_interval_start_date, trough_interval_end_date
detectability_floor_pp
amplitude_to_floor_ratio
```

`peak_interval_start_date`/`peak_interval_end_date` (and the trough
equivalents) are populated whenever the status is `interval` *or* `point`
(a single-month interval); only `unresolved` leaves them blank. See
[Report Export Columns](../report-columns.md) for the full schema.

These populated bounds are **bounds of equivalent evidence**, not a
statistical confidence interval and not a precise date merely narrowed to a
range: every month inside `[interval_start, interval_end]` is equally
consistent with the observed record, and none within that span is preferred
over another. Read this alongside `unresolved`, not instead of it: an
`unresolved` year's blank interval is not "zero evidence" any more than an
`interval` year's populated bounds are "we actually know it more precisely
than we're publishing" — both are honest statements about what the record
can and cannot distinguish, and neither may ever be described as an exact
published point.

The one-row summary (`CatchmentAnalysis.summary_row()`) gains
`n_peak_timing_years`, `n_trough_timing_years`, `n_zero_months`,
`zero_month_fraction`, `n_whole_zero_years`, `pixel_support_status`, and
`timing_evidence`, appended after the existing `n_timing_years` field --
existing column positions before it are unchanged.

### `boundary_status` and `timing_status` are separate concepts

`boundary_status` (`confirmed`/`provisional`) describes selection and data
admissibility -- whether the chosen boundary month is well-observed and
consistent with neighbouring years. `timing_status` (`point`/`interval`/
`unresolved`) describes temporal identifiability -- whether that month is a
defensible exact date at all. A cycle can have high `selection_support`
(good data/window quality) while its `timing_status` is `unresolved` (a
flat or below-floor year): the two axes are independent, and a report must
not conflate them into one `confidence` field.

Unresolved timing forces `boundary_status="provisional"`,
`status="partial"`, and confidence capped at `low`. Only rows with
`boundary_status="confirmed"` **and** `timing_status="point"` may anchor a
historical condition baseline (`recharge_condition`/`refuge_condition`);
`interval` rows may retain an internal operational date for phase
continuity, but monthly phase uses `phase_status="interval_boundary"`, and
unresolved rows use `phase_status="unresolved_cycle"` (no rising/receding
claim).

### Report cards

"High confidence years" is replaced by two separate cards: **"well-observed
years"** (data/window quality, `selection_support >= 0.8`) and
**"point-identifiable boundary years"** (`timing_status == "point"`). A new
**"observability"** card reports zero-water fraction and whole-zero-year
count alongside how many years support both peak and trough timing. A
marginal record routed to events now gets explicit copy: *"Marginal
seasonal signal; annual timing is insufficiently identifiable. Wet events
and low-extent spells are reported; exact hydrological-year boundaries are
withheld."*

### Percentage-only vs pixel-backed records

`pixel_support_status` (`"available"`/`"unavailable"`) is now a first-class,
published field. Percentage-only inputs (no `n_water`/`n_valid`/`n_invalid`/
`n_aoi`) always report `"unavailable"`, and their `min_peak_water_pixels`
threshold is not consulted -- the detectability test is skipped for that
condition rather than failed. The current real-catchment evidence base is
entirely percentage-only; `min_peak_water_pixels` is calibrated and
evidenced on synthetic data only. See
`docs/decision-policy-0.2.0.md` for the full evidence-limits statement.

### `min_informative_years` is not `EvidenceThresholds.min_timing_years`

`min_informative_years` is a new, separately calibrated threshold on the
established path. It is deliberately not merged with, aliased to, or
re-derived from the challenger path's `EvidenceThresholds.min_timing_years`
(which ships its own documented relaxation via
`_apply_min_timing_years_override`). The two are calibrated independently
and must be read as independent thresholds.

### Policy identifier

`decision_policy` changes from `established_0_1_1` to `established_0_2_0`.
Code that pattern-matches on the exact string must be updated.

## Upgrade checklist

- If your code reads `route` and assumed `regime in {"seasonal", "marginal"}
  implies per_year_detection`, add a check for `timing_evidence` (or just
  branch on `route` directly, which already reflects it).
- If your code reads `peak_date`/`trough_date` from the compact CSV and
  assumed they are always populated for a resolved year, check
  `peak_timing_status`/`trough_timing_status` first, or read the interval
  columns as a fallback.
- If your code reads `n_timing_years` expecting it to reflect the weaker of
  peak/trough support, note that it does not: it is peak-derived only. Read
  `n_peak_timing_years` and `n_trough_timing_years` directly if you need
  both, or `min()` them yourself.
- If your code builds condition baselines from `boundary_status=="confirmed"`
  alone, add the `timing_status=="point"` condition -- the baseline gate is
  now stricter.
- If your code parses the KPI card deck by label, "high confidence years" no
  longer exists; read "well-observed years" and "point-identifiable boundary
  years" instead.
