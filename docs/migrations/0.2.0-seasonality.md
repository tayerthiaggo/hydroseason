# Migrating to 0.2.0: Seasonality, Timing Recurrence & Field Names

HydroSeason 0.2.0 introduces the frozen sole method policy `hydroseason-v0.2.0`, replacing heuristic Signal-to-Noise Ratio (SNR) seasonality routing with a mathematically grounded circular timing recurrence gate, and formalizes calendar-month summary field names.

---

## 1. Removal of SNR Routing & Adoption of Timing Recurrence

### What changed
- In previous versions, seasonality classification relied on empirical amplitude ratios and SNR thresholds that could conflate episodic high-amplitude flood events with true recurring seasonality.
- In v0.2.0, SNR routing and selectable `seasonality_policy` arguments have been **completely removed**.
- The sole runtime method `hydroseason-v0.2.0` mandates a circular timing recurrence gate based on detrended extrema:
  - **Detrending**: A centred $2 \times 12$ moving average removes decadal and multi-year trend-cycle components without extrapolating beyond observed data.
  - **Five-Detectable-Year Guard**: A record must contain at least **5 detectable years** (years where positive peak-to-trough extent exceeds $3 \times$ the detectability floor). If fewer than 5 detectable years exist, the record is routed to `aseasonal`.
  - **Weighted Kuiper Conjunction**: Weighted circular Kuiper uniformity tests are performed independently on peak and trough calendar-timing sets (using 999 Monte Carlo rotations). A catchment is classified as `seasonal` if and only if **both** peak ($p < 0.05$) and trough ($p < 0.05$) tests reject uniformity.
  - **Equivalent-Month Sets**: Broad or tied extrema share unit annual weight equally across all eligible calendar months rather than forcing false precision.

### Code Migration
Remove any explicit `seasonality_policy` or `--method-policy` options from scripts, API calls, and workflows. Timing recurrence is now the built-in, mandatory scientific standard.

```python
# Before (0.1.x / early candidate):
# result = run_hydroseason(..., seasonality_policy="timing_recurrence")

# In 0.2.0:
result = run_hydroseason(...)
```

## 2. Mean-Monthly Seasonality Names

HydroSeason 0.2.0 gives the two calendar-month summaries names that describe what they measure: the maximum and minimum of mean monthly observed extent.
The old `climatological_peak_month` and `climatological_trough_month` names were deprecated aliases and are now removed from the live Python API and from `CatchmentAnalysis.summary_row()`.

### Update Python consumers

Replace attribute access on both `WaterRegimeAssessment` and `CatchmentAnalysis`:

```python
analysis.mean_monthly_peak_month
analysis.mean_monthly_trough_month
```

The values and their null semantics are unchanged. They remain `None` when the record does not support an identifiable annual timing, and otherwise are 1-based calendar months computed from mean monthly observed extent.

### Update summary consumers

`CatchmentAnalysis.summary_row()` now contains only the canonical keys:

```python
row["mean_monthly_peak_month"]
row["mean_monthly_trough_month"]
```

Code that reads a generated case-study summary should use those same keys.
Previously checked scientific and case-study artifacts are historical records; their serialized headers are intentionally left unchanged and are not an indication that the removed aliases remain available in new analyses.

The route name `fixed_climatological_window` is unrelated to these field names and remains unchanged.
